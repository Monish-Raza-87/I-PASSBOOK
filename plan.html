SECTION 0

Read this first: the IR list, and whether it is exposed

Now measured

You said the IR data is sensitive, so this was the one finding that could change the order of the whole plan. It is no longer a hypothesis — I tested it on 2 October 2026. It resolved in the safe direction, with one real exception.

The app's main IR list does not go through the logged-in backend. It fetches the list straight from Google, and the request carries no credentials at all — no token, no cookie. Whatever that path can reach, anyone can reach. It is tried first, and it returns before the protected route is ever consulted.

How serious that is depends entirely on one sharing setting — so rather than ask you to read a status line, I fetched the exact URL the app uses with no credentials at all. The result is below, and it is the answer to the question this section was written to raise.

Measured, 2 October 2026 — the good news

I stopped guessing and tested it. The exact URL the app uses to read the IR sheet, fetched with no login at all, returns HTTP 401 — a sign-in page, not data. The Drive root folder returns HTTP 401 as well.

So the no-login path has been dead all along, exactly as you said, and the protected backend has been serving the list. Your data is not exposed through either of those two doors. This was the one finding that changed the whole order of the plan, and it has resolved in the safe direction. The first item on the list is no longer an emergency.

But one door is open — the legacy workbook

The legacy workbook is readable without any login. I fetched its first sheet with no credentials and got a 200 and real content back. That means the file is link-shared, and link-sharing is per file, not per tab — so every tab in it is readable by anyone who has the file's address.

Why that matters more than it looks: the file's address is written in the app's own source code, and the source code is in a public repository. So the address is not a secret. Anyone who reads the repo has everything they need to open the legacy data.

The fix is one setting — Share → General access → Restricted in the legacy workbook — but it has a cost, and I am not going to pretend otherwise. The workbook is link-shared precisely because the 🏛 Legacy button embeds it live. Restrict it today, and that button stops working.

So it is a choice, and it is yours:

  • Restrict it now — the leak closes today, and the Legacy button goes dark until Phase 0 finishes. The legacy data is still in the workbook and still safe; it is simply not visible inside the app for a while.
  • Do Phase 0 first — render the legacy view from backend data, as the plan already says, and then restrict the workbook with nothing lost. Slower to close the door.

My recommendation is the first one, because how long the data has been reachable matters more than whether one button works this week. But it is a real trade and you should make it knowingly.

Also in the public repository, and worth knowing

Beyond that one workbook, the public repo also contains the app's backend address and the internal addresses of the IR sheet and the Drive root folder. Those two are not open today — I tested them — so nothing is leaking through them right now. But publishing the addresses means that if the sharing on either is ever changed by accident, the data becomes readable instantly, by anyone who has read the repo, with no further warning and no sign on screen.

I checked the obvious thing too: there are no passwords, API keys or private keys committed anywhere in the repository.

Phase 0 removes this as a side effect. Once the list comes through the backend instead of the browser reading the sheet directly, the app no longer needs the sheet's address at all — so it comes out of the source, and the public repo stops naming your internal documents.

What travels over that path, if it is live — per IR:

  • IR number, date raised, incident date, current status
  • Drone serial number
  • Who is reporting — a named person
  • Their email address
  • The free-text description of the problem, and what support was requested
The two findings that hold either way

1. A read path that only falls back on failure. The app tries the no-login route first and switches to the protected one only when that fails. Nothing warns you if the sharing setting ever changes — and then dead code becomes a live feed, silently, with no deploy and no sign on screen.

2. Every Indrones account can read the whole list. If the sheet is company-restricted, then customer names, email addresses, drone serials and problem descriptions are readable by every account in the company — regardless of what the app's own per-section permissions allow. That may be exactly what you want. Today it is a side effect rather than a decision.

The fix is small and it does not need the big migration. The protected route on your backend already exists and already reads the same records — the app simply prefers the other one. Phase 0 is: stop the browser reading the unauthenticated source, route the list through the backend you already have, and make the sharing setting something the app never depends on. Then it stops mattering which way the setting points.

The only cost is that the list becomes slightly slower, because it goes through Apps Script. Phase 3 removes that cost entirely.

Also to verify in Phase 0: the sharing setting on your Drive root folder and the evidence folders. Nothing in that folder should be reachable without signing in either. The legacy workbook is embedded live today, which is what forces it to stay link-shared — Phase 0 renders it from backend data instead.

SECTION 2

How this build stays safe

Six rules that apply to every phase below. They are the reason the order is what it is.

  1. The net goes up before the risky change, not after. Backups are built and tested while nothing is at stake, so the migration is the safest thing we do, not the scariest.
  2. Nothing is ever overwritten. Every backup is a new, dated file. This is already the rule in your code, and it is what makes the realtime sync to your servers safe — the sync accumulates history instead of faithfully copying a mistake.
  3. A backup nobody has restored from is not a backup. Before the migration, we rebuild the app from an export file once and prove it works.
  4. Readable, not just restorable. A spreadsheet you can open on your phone tomorrow morning, plus raw data that a program can rebuild from. Both, because they do different jobs.
  5. The backup is the most sensitive thing in the system. A full readable copy of every IR, every customer email and every user account is a bigger prize than the app itself. It never gets shared, and its folder permissions are the tightest in the whole setup.
  6. Failures announce themselves. Success is silent; failure sends you a message. A backup that quietly stopped working three months ago is worse than no backup, because you were relying on it.
One honest trade on the backup

You want to read it in Excel tomorrow morning, so it cannot be encrypted in a way that only a program can open. That means the backup folder is a complete, readable copy of everything. The protection is therefore folder permissions and your account's security, not a password on the file — and that is worth knowing deliberately rather than discovering later.

PHASE 0

Close the leak

Urgent Days, not weeks

Nothing about the app's look changes. The data simply stops being public.

  • Remove the direct read from the browser. The list comes through the protected backend route that already exists.
  • Take both Google sources from link-shared to restricted sharing. The backend still reads them, because it runs as their owner.
  • Rebuild the Legacy view from backend data instead of embedding the live workbook, which is what forces it to stay link-shared today.
  • Verify the sharing on your Drive root folder and the evidence folders.
  • Add a check to the test suite that fails if a public read path ever comes back.

What you'll see: the list takes about a second longer to appear. Nothing else. What changes: your IR data stops being readable by strangers, today, without waiting for any of the rest of this plan.

PHASE 1

The safety net

Build second 1–2 weeks

This is the phase you care about most, and it is deliberately before the migration. It works on the store you have today, so it needs nothing else to be finished first.

The change journal

A small record appended as work happens, so a crash at 4pm costs you minutes instead of a whole day. Written inside the same server call that already saves your edits, so it costs nothing extra.

The nightly full export

Every night: a Google Sheet you can open on your phone with a tab per record type, plus CSV files, plus the raw data a restore actually rebuilds from. Into a dated folder.

The rotation

14 daily, 8 weekly, 12 monthly, one yearly forever. About 625 MB steady, flat forever — instead of 55 GB over ten years, which would have filled your entire Google account.

The yearly archives

IRs that leave the 12-month window are exported once into a dated archive file that is never touched again. Small, permanent, and never rewritten — so the thing that grows forever is not the thing written every night.

Backup health, visible

The export records its own success, and the app shows "Last backup: last night, 23:40 ✓" on the admin screen. You'd see it every day without doing anything.

Failure is loud

An email on failure only. Plus an independent daily check from your own GitHub repo — it lives outside Google, so it still barks if the whole Google side stops.

The restore rehearsal

A script that rebuilds the store from an export, run once for real into a scratch folder. Until that has happened, we are guessing — and guessing is what fails at the worst moment.

Drive → your servers

Your part. Point the sync at the backup folder, never at the live working folder — mirroring the live data in realtime would copy an accident within seconds.

Why this ordering is the safe one

By the end of Phase 1 you have a readable copy of everything, refreshed nightly, copied to machines you own, and proven restorable. Then we touch the data layer. If the migration goes wrong, the answer to "can we get it back?" is already yes, and it was answered before anything was at risk.

PHASE 2

The seam

Build third Internal — you see nothing

One file gets one job: talking to the backend. Everything else asks it. This is a small change that makes two big ones survivable.

Your app is one 10,000-line file, and backend calls are scattered through it. That single fact is what makes replacing the backend frightening, and what makes building new screens awkward.

  • Every backend call moves into one file. Nothing else calls the backend directly.
  • It makes the migration survivable: swapping the backend becomes changing one file instead of hunting through ten thousand lines.
  • It lets work run in parallel: new screens get built against the seam while the migration happens behind it.
  • No build step, no npm, no new stylesheet. A library can simply be placed in the repo — your vendored PDF library is already the proof of that.
PHASE 3

The migration

Build fourth The big one

The app stops asking a server for data and asks a database directly. This is what makes it fast, and it is the permanent fix for Section 0.

Why the free plan is safe, in numbers

At your size — around 500 IRs, 150 of them live, about 15 people using it:

Per dayUsedFree limitOf the limit
Writes — saves, statuses, new IRs, nudges~20020,0001%

Writes and storage were never the risk, and they get safer as the archive grows. Reads are the only thing that can bite, and only if caching is skipped. Caching is therefore not an optimisation; it is what makes the free plan safe. And there is no payment method on the account at all, so no mechanism exists that could produce an invoice — the worst case is the database refusing until the quota resets at midnight Pacific, never a bill.

PartWhere it lives after the migration

Three things worth knowing up front

  • Permissions get encoded into the sign-in token. Your access model is department-based. Putting each person's departments into their sign-in token means permission checks need no lookups at all — fast and simple. The cost is that a change takes up to an hour to reach someone who is already signed in.
  • Departments could become Google Groups, which would delete a private list the app maintains today — and delete a known bug in it at the same time.
  • Insights reads precomputed counts, not every IR: twelve small documents a year instead of thousands of reads. The archive files stay in Drive for questions nobody anticipated, loaded only when you actually ask one.

How the data moves, safely

  1. A copy migration, never a move. The old store is left exactly as it is, untouched, for three months.
  2. It verifies itself: every record compared before and after, and it refuses to switch if anything disagrees.
  3. Your nightly backup is the rollback path — and by now it has been rehearsed.
  4. An archived period is loadable on demand. When you click a bar for a year that is past the 12-month window, the app offers one button — "Load this year from the archive" — so you never hit a dead end, and you never wait unless you asked.

PHASE 5

Bridges, languages, polish

Last

The pieces that connect outward, once everything inward is solid.

The three Google bridges

  • Chat — IR notifications into a space. The webhook address is a secret, so it lives on the backend and never in the app's code, where anyone could read it and post as you.
  • Drive — one evidence folder per IR, inside your master folder. Files stay yours, at every age, even after the app forgets the link.
  • Sheets — the customer intake form, and your legacy workbook, both read by the backend rather than published.

Hindi and Marathi

There is no translation system in the app at all — every label is hard-coded English. The single most useful thing here is to put the indirection in now, while only English ships, because retrofitting it later is the expensive version of the same job. The translations themselves then become one file rather than a rewrite.

The cold spare

Planned now, built last. Your app's screens are static files that would still load even if Google turned everything off — it is the data that would vanish. So the spare is a mode that opens a backup file you already have and shows your records read-only. Slower, and not for everyday use. It exists so that the answer to "what if the terms change" is a file on your own machine, not a phone call.

SECTION 10

Honest limits

The parts where I would rather set the expectation now than explain later.

  • "100% data safety" is not a thing anyone can promise — not me, not Google. What this plan does instead is make a loss survivable: two independent copies, one of them on machines you own, plus a restore that has actually been performed.
  • "Forever free" is not a promise either. What is true is stronger and narrower: there is no payment method, so no invoice can be created; and the free quota is used at about a tenth. Terms could still change, which is precisely what the cold spare is for.
  • Phase 0 makes the list slower. That is a real regression, accepted deliberately, and Phase 3 removes it.
  • The board needs a new field ("current stage") or it will be guessing from an append-only list.
  • A permission change takes up to an hour to reach someone already signed in, once permissions live in the sign-in token.
  • The archive seam is real. Counts cover everything; clicking into a period older than a year loads it on demand rather than instantly.
  • Translations and legal text need a person. Software can carry them; it cannot vouch for them.
